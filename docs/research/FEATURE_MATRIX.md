# LoxiLB Feature Matrix for OpenStack Octavia Integration

**Research date:** 2026-08-11  
**Evidence policy:** Official LoxiLB documentation/upstream source and official OpenStack Octavia documentation only.

---

## Legend

### LoxiLB support

- **YES / CORE** — demonstrated as a LoxiLB core/standalone capability.
- **YES / K8S** — demonstrated through Kubernetes-side integration/control components.
- **PARTIAL** — capability exists but its semantics/scope do not fully match the requested form.
- **NOT EVIDENCED** — no sufficient official evidence found for the required form.

### Octavia mapping

- **DIRECT** — close resource/semantic match.
- **ADAPTER** — possible with translation/validation/reconciliation.
- **PROVIDER-INFRA** — backend architecture function rather than a native Octavia object.
- **PARTIAL** — some semantics map, some do not.
- **NO/MVP** — should be rejected/deferred in the first provider implementation.

## 11. Features that must not be misclassified

| Incorrect claim | Correct classification |
|---|---|
| “LoxiLB L7 means Octavia L7 is supported.” | **Incorrect.** L7 is documented through K8s Gateway/Ingress. Generic Octavia L7Policy/L7Rule mapping is not proven. |
| “Active-active implies hitless failover of existing connections.” | **Incorrect.** BGP ECMP active-active is documented; connection sync is documented separately for external active-backup. |
| “`--cluster` means all configuration is replicated automatically.” | **Incorrect.** Documented peer sync concerns connection/HA state; provider must still reconcile desired service configuration. |
| “Service sharding is a generic LoxiLB scheduler.” | **Incorrect.** Official sharding automation is implemented by `kube-loxilb`. |
| “Health monitoring is automatic by default.” | **Incorrect.** LoxiLB active endpoint monitoring is off by default. |
| “Container deployment is unprivileged.” | **Incorrect.** Official examples run privileged with `SYS_ADMIN`. |
| “BGP ECMP works without network support.” | **Incorrect.** Upstream network devices/hosts must support ECMP. |
| “HTTP over TCP means L7 HTTP features.” | **Incorrect.** L4 pass-through does not implement HTTP routing/policy/TLS semantics. |

## 12. Recommended implementation priority

### P0 — prove before coding the Provider Driver deeply

- pinned LoxiLB release/API behavior,
- VIP/service CRUD,
- member add/remove/update behavior,
- algorithms,
- active probe semantics,
- API TLS/auth,
- BGP route advertisement,
- ECMP failure behavior,
- active-backup connection sync,
- multiple services/VIPs per shared instance.

### P1 — Provider Driver MVP

- LB/Listener/Pool/Member lifecycle,
- restricted health monitor mapping,
- direct algorithms only,
- desired-state reconciler,
- status callbacks,
- durable resource mapping,
- management-network API client.

### P2 — HA/scale-out provider infrastructure

- node inventory/capacity,
- placement/sharding,
- config replication,
- BGP/ECMP policies,
- node health/fencing,
- failover,
- state-sync topology,
- scale-out benchmarks.

### P3 — optional feature expansion

- broader HM semantics,
- provider flavors/capabilities,
- TLS/L7 investigation,
- provider-specific LoxiLB features not represented in vanilla Octavia.

## 15. Bottom-line feature classification

### Proven core features worth building the Octavia MVP around

**eBPF L4 dataplane, VIP/service/endpoints, RR/WRR/persist/hash/LC, active endpoint probes, REST API, GoBGP, BGP active-active ECMP, BGP/L2 active-backup mechanisms, and external active-backup connection synchronization.**

### Features that are real but should be classified as Kubernetes integration

**Kubernetes Service automation, kube-loxilb endpoint/service discovery, K8s HA election orchestration shown in the guides, Gateway API/Ingress L7 control, TLS ingress via Kubernetes secrets, and Kubernetes service sharding.**

### Features the OpenStack provider must add around LoxiLB

**Octavia hierarchy translation, durable mapping, desired-state reconciliation, multi-node configuration fan-out, node placement/sharding, HA orchestration/fencing, BGP fabric policy, status translation, and safe asynchronous lifecycle handling.**
